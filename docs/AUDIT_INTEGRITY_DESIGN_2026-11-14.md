# 审计完整性：方案评估与实施设计

状态：已开始虚构 M1 本地链原型，详见 [第一步记录](AUDIT_STEP1_2026-11-14.md)；**未实现备份审计迁移、外部锚定或 R2 上传**。仅允许虚构资料实验；当前 G1、独立评审和真实资料门禁仍未通过。

## 对所提方案的判断

将审计放进加密库、按顺序形成链、用备份清单绑定快照，以及在库外保存检查点，方向可行，但原组合不能独立保证防篡改或防回滚：

1. **普通哈希可重算。** 能写数据库的人可以改旧条目并重算后续 SHA-256；删除尾部也可形成自洽的新链。它只能在与可信的、较新的外部检查点对比时发现此类变化。
2. **数据库与清单同退无法发现。** 数据库、库内锚点和对应 manifest 一起被替换成旧版本时，彼此仍然匹配。清单 HMAC 能验证持密钥者产生的内容是否匹配，不是公开可验证的数字签名，也不证明这个版本是最新版本。备份口令或恢复码泄露后，相应备份完整性与保密性都受影响。
3. **快照一致性。** 当前 `backup_job.run` 先执行加密快照，之后才写 `backup_created`；如果从实时库读取链头写进清单，快照与清单可能不一致。备份上传、失败等事件发生在快照之后，也不能假装已包含在这次快照中。
4. **远端前缀不等于只追加。** 原 R2 sink 的先 HEAD 再 PUT 不是原子创建，HEAD 的服务端异常也会被忽略；目前已改为 `If-None-Match: *`，仅经假客户端验证。R2 [条件写入](https://developers.cloudflare.com/r2/api/s3/conditional-operations/)支持该参数，但删除后同名对象仍可重新创建；[Bucket Lock](https://developers.cloudflare.com/r2/buckets/bucket-locks/) 在规则的保留期内禁止覆盖和删除，规则与管理权限需要独立保护。不能仅凭路径声称远端不可变。
5. **明文内容和元数据。** 上传 `audit.log` 会泄露事件；仅上传哈希也可能泄露频率、设备标识或可猜测事件。加密数据库不能保护操作系统分页、日志、旧明文文件或密钥所在进程。
6. **历史/不完整和并发。** 已有备份、`audit_events` 与明文 `audit.log` 没有链或外部锚点；不能静默宣布历史可信。并发写入必须串行化序号与头，明确失败时操作如何处理。周期上传可能失败，超出最近锚定时间的事件不具备外部回滚检测。

## 推荐分层设计

### 1. 独立的版本化加密审计链

- 在实验 vault 内增加独立 `audit_chain`，不直接改业务 `audit_events`；两者事件范围、迁移和权限需明确。每条包含稳定 vault ID、格式版本、单调序号、事件类型、受控字段、UTC 时间、前一哈希和本条哈希。只接收允许字段，禁止口令、恢复码、邮件正文等秘密进入审计。
- 使用严格定义的规范化序列化和编码：限定字段类型、UTF-8、确定性键序，拒绝 NaN 与重复 JSON 键；明确版本、域分离、长度边界、创世值和哈希编码。示例：`SHA256(domain || prev_hash_bytes || canonical_event_bytes)`，序号包括在规范化内容中。序号和哈希约束要检查缺口、重排和重复。
- 与业务状态同库、同一个 `BEGIN IMMEDIATE` 事务内校验上一条并追加；写审计失败则对应受保护操作失败并回滚。跨数据库/外部上传无法天然形成原子事务，需用本地 outbox、幂等重试与明确状态处理。单纯 SQL trigger 无法抵御可任意修改数据库及代码的攻击者。
- 校验器逐条重新计算并报告第一个异常；无外部检查点时报告 `LOCAL_CHAIN_CONSISTENT_UNANCHORED`，不得报告“防回滚已通过”。

### 2. 与备份快照绑定

- 在已完成的**加密快照**中验证链、读取 `(vault_id, format, seq, head)`，再将结果纳入现有独立密钥保护的 manifest HMAC。应先检查快照再发布归档，不能从仍在变化的源库读取链头。
- 恢复时先验证 manifest HMAC 和数据库摘要，再验证快照内的链及其头与清单一致。结果只能表明**这份快照内部一致**；恢复旧快照时应正常标记其时间点，而不是直接判为被篡改。带可信外部水位时再判断是否落后，并允许用户明确选择从旧备份恢复，记录为有意回退，不覆盖外部历史。
- `audit_anchors` 若保留，只是本地便利索引，不能充当独立信任根，也不应为了记录一个覆盖自身的头引入循环依赖。快照之后的备份创建/上传结果作为后续新事件，在下一次检查点覆盖，或者使用单独的已认证备份结果记录。
- 为旧备份定义 `LEGACY_UNANCHORED` 状态；不得在缺少字段时默认为完整通过。迁移从新创世点开始，旧日志仅作未经证明的历史参考；不得删除旧明文，直到用户明确决定其处置。

### 3. 外部独立检查点（后续阶段）

- 先在本地实现、测试 `checkpoint`，包含格式版本、随机 vault ID、单调序号、头、前一个 checkpoint 摘要和创建时间。使用与数据库/备份口令分离的专用认证密钥；多设备或第三方验证需要可验证签名及可信公钥分发/轮换，不能把普通哈希当认证。
- 明确独立信任边界：最少把最近已确认的 checkpoint 和身份存到不与库同生命周期、不能由普通写入凭据覆盖的地方；仅与同一受控账户中的旧数据对比不能抵御该账户整体回滚。高威胁场景需要独立管理的不可变存储或第三方见证，且需可信的最新水位。远端列表被过滤、离线、钥匙丢失或未锚定时应标记 UNKNOWN / UNANCHORED，而不是声称无回滚。
- 若日后采用 R2，单独前缀或桶，使用具最小权限的凭据与原子条件创建，并配置覆盖所选前缀的锁定与保存周期。确认规则和管理员权限边界、成本、恢复、分页与失败告警；仅通过前缀本身或普通 `PutObject` 不能获得只追加。每日频率只是目标，需持久 outbox、上传回执、重试及滞后告警。

## 本批独立修复

当前备份清理原先将 `backups/` 下所有返回对象纳入保留策略，会误删未来 `backups/audit/` 检查点；现仅选择指定备份前缀的直接子项 `jarvis-backup-*.jvault`。S3 列表原只读第一页，现分页并对缺失/重复续页令牌失败关闭。仅用本地模拟对象测试，未访问 R2；对象存储列表在并发变更下的整体快照一致性仍不由此保证。

## 实施次序与验收

1. 明确事件范围、规范化格式、信任假设和旧数据策略；设计审查后，用虚构数据实现链表和同事务追加。
2. 测试并发、多进程、异常回滚、格式边界、内容/顺序/中间及尾部删除、攻击者重算整链等；明确无锚点时不能发现的案例。
3. 将头从备份快照写入认证清单，测试并发快照、旧备份、恢复、错误密钥、篡改，以及完整旧数据库加旧清单的回滚无法仅靠本地检测的反例。
4. 设计独立 checkpoint 密钥管理、可信水位和离线恢复；本地模拟条件写入、服务故障、撤销、并发、缺失及回滚后，再单独征得服务连接授权并部署。
5. 独立安全评审与异机恢复均通过前，保持真实资料与正式发布关闭。
