# Jarvis 设计决策记录

决策以时间倒序或 ADR 编号累积。已接受的决策不要无记录地改动；后续变化建立新条目并链接旧决策。

## ADR-014：从现有实现独立重设 Jarvis 产品与技术基线

- **日期：** 2026-11-08
- **状态：** Proposed，供用户评审；不自动取代 ADR-006 至 ADR-013 已确认的需求和授权边界。
- **背景：** 最近记录的 57 个脚本项包含 `G1_GATE=OPEN` 仍按 PASS 计数的驱动诊断；它们证明若干合成流程可运行，却没有真实 AI 效果评估、可发布的安全存储、真实账户、完整客户端和多设备同步。旧路线把试验、产品版本和发布门槛混用。
- **建议：** 以[新版产品基线](JARVIS_V2_PRODUCT.md)和[架构](JARVIS_V2_ARCHITECTURE.md)为独立方案；先在虚构数据上证明信息到行动的纵向闭环和 AI 评测，再过本机存储/恢复门槛，之后逐来源授权接入。现有代码是可复用资产，不是必须沿用的技术决策。交付顺序见[新版阶段计划](JARVIS_V2_EXECUTION.md)。
- **对已确认目标的影响：** Windows、网站、多设备端到端密文同步、电影 HUD、按键语音和 X 轻量入口保留为目标 V1；陪伴模式仍冻结。新的 R0/R1/R2 是工程增量，不表示这些长期目标被删除。若目标范围需要缩减，须另立决策。
- **下一次复核：** M1 纵向闭环评测完成后，结合质量、开发成本和安全证据决定是否采纳为正式基线。

## ADR-001：本地优先；多设备服务与同步另行决策

- **日期：** 2026-11-06
- **状态：** Superseded by user platform requirement; local-first principle retained
- **背景：** 邮件与私人收藏敏感，需要降低默认云端可见性。
- **决策：** 用户已确认本地优先，同时要求 Windows 桌面、网站登录和多设备使用；同步实现必须先确认加密与数据可见性。
- **结果：** 产品需要身份/同步服务的设计，但不得默认把明文个人资料放在服务器。

## ADR-002：建议与执行分离

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** 模型可能误判，也可能将邮件/帖子中的恶意指令当作请求。
- **决策：** LLM 只产出 `AISuggestion`；策略与审批服务决定是否产生 `ActionProposal`；外部连接器只接收经过授权的、经批准的结构化动作。
- **结果：** 首版不能自动发送、永久删除或发帖；动作载荷必须锁定并审计。

## ADR-003：参考 HUD 氛围，原创实现

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** 用户希望界面接近电影 HUD；HALOFLUX 与 Amber Protocol HUD 是视觉参考。
- **决策：** 使用深色空间背景、青蓝/琥珀状态色、环绕面板、原创中心光环；不复制参考仓库的源码、图形资产、音乐、命名或具体构图。HALOFLUX 当前为 PolyForm Noncommercial License，故尤其不作为产品实现依赖。
- **结果：** 可保留相似的高层视觉意图，同时降低许可冲突并保持 Jarvis 的可用性。

## ADR-004：原型阶段先使用无依赖浏览器预览

- **日期：** 2026-11-06
- **状态：** Accepted for prototype
- **背景：** Python/Streamlit 启动环境受 Windows 更新/CET 问题影响，用户无法立即查看界面。
- **决策：** 用单文件 HTML 验证界面；长期应用服务仍采用 Python；长期自定义 HUD 前端采用 React + Vite + TypeScript。
- **结果：** 原型双击即可打开；业务数据与真实连接器尚未实现。

## ADR-005：从通用后台转向原创 HUD 工作台

- **日期：** 2026-11-06
- **状态：** Accepted direction
- **背景：** 用户明确指出首版 Streamlit 式后台不符合目标，期望电影式 Jarvis 视觉；参考了 HALOFLUX 与 Amber Protocol HUD。
- **决策：** HUD 首屏采用中央助手状态核心、左右任务舱、底部内容/审批带；以状态驱动有限动效，减少纯装饰和未经用户要求的摄像头/语音/地图功能。
- **结果：** 当前浏览器预览已转为深色空间风格；各模块保持可读、可用。所有视觉资产清洁原创，不拷贝参考仓库的代码或素材。

## ADR-006：产品核心定位为个人信息与行动中枢

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** 产品需要明确在邮件、收藏、知识和待办之间的主线价值。
- **决策：** Jarvis 统一个人信息与行动，把分散来源汇总为可理解、可执行、可追溯的工作流。
- **结果：** 首页优先呈现跨来源的待处理事项、任务和审批；各模块以来源追溯和任务关联作为共同基础。

## ADR-007：首版聚焦邮件与待办，其他能力做轻量入口

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** 四大能力同时做完整会拉长首版周期。
- **决策：** 邮件和待办走完整主流程；X 收藏/点赞和知识库以轻量收集、浏览、基础整理起步。
- **结果：** 轻量入口边界在原型阶段验证，完整智能整理进入后续路线图。

## ADR-008：本地整理可规则自动化，外部沟通逐项批准

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** 用户希望减少重复性整理，同时保留对外沟通控制权。
- **决策：** 用户可创建作用于可逆低风险整理动作的规则；发送邮件、发帖等外部沟通逐项审批；删除类操作另有明确确认。
- **结果：** 规则需先预览目标、显示日志、支持暂停和撤销，默认规则范围需再确定。

## ADR-009：首版支持按键启动语音

- **日期：** 2026-11-06
- **状态：** Accepted; provider open
- **背景：** 用户希望语音输入与播报，但不要求常驻助手。
- **决策：** 首版纳入按键启动语音输入和语音播报，不启用常驻监听；云 ASR/TTS 的数据流需清楚告知。
- **结果：** 需要麦克风状态、识别文本预览、取消/打断控制；服务提供方待选。

## ADR-010：Windows 桌面与网站登录支持多设备

- **日期：** 2026-11-06
- **状态：** Accepted; key lifecycle details open
- **背景：** 用户需要多设备登录、Windows 桌面体验与网站登录，同时选择资料本地优先。
- **决策：** Windows 桌面和 Web 登录同一 Jarvis 账户；设备保存可用的本地副本，跨设备内容端到端加密，云端只保存密文和最低限度的路由/版本元数据。
- **结果：** 后续需设计密钥恢复、设备撤销、密钥轮换和离线冲突策略。真实账户接入前完成威胁模型。

## ADR-011：以统一 Capture Inbox 接入多应用内容

- **日期：** 2026-11-06
- **状态：** Accepted; per-source integration open
- **背景：** 用户希望从微信、X、浏览器、小红书、邮件及其他应用收集信息。
- **决策：** 所有来源进入统一 Capture Inbox；优先使用官方 API 或用户主动选择的系统分享、浏览器剪藏、快捷键/剪贴板、URL 和文件导入。每个连接器注明权限与数据范围。
- **结果：** 没有可用官方个人数据 API 的应用仍可通过用户主动捕获支持；不抓取私有接口、Cookie 或聊天数据库。不同来源的首版解析深度需逐项核定。


## ADR-012：先实现底层本地核心，前端暂缓扩展

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** HUD 原型可点击但仅使用浏览器 localStorage 模拟数据；业务域、持久化、助手隔离与记忆权限尚未形成可供前端调用的真实底层。
- **决策：** 暂停 HUD 新功能与前端工程迁移。先实现 FastAPI + SQLite 本地核心：数据合同、迁移、助手/会话、记忆访问网关、续聊卡与待办；安全和加密完成前仅使用合成数据。
- **结果：** HUD v0.3 作为展示壳保留；底层 API 与领域规则稳定后再接入。


## ADR-013：Jarvis 先行，陪伴通道保留

- **日期：** 2026-11-06
- **状态：** Accepted
- **背景：** 用户希望先做 Jarvis，陪伴需求之后重新梳理。
- **决策：** 暂停陪伴模式的需求细化、人格、记忆和交互扩展；保留已有通道、数据结构与历史资料。当前开发聚焦 Jarvis 的待办、邮件、信息收集、知识与可审计审批。
- **结果：** 原先“双助手优先增量”的交付顺序被调整；是否及何时恢复陪伴功能由后续需求确定。
