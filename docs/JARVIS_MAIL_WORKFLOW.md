# Jarvis 本地邮件工作流 J1

**状态：** 开发切片，合成数据；2026-11-06。

J1 让 Jarvis 在无账号、无模型的环境中操作合成邮件：导入模拟邮件、搜索和本地分流、创建/修改回复草稿、生成待审发送快照、由用户批准或拒绝。全部地址必须使用 .invalid 测试域名；数据库尚未加密，不能保存真实邮件。

邮件与草稿仅属于当前 owner，服务只接受 Jarvis 身份。整理状态仅作用于本地副本；不修改外部邮箱。生成草稿内容由调用方提供，当前没有 AI 生成或摘要能力。

发送提案包含账号、收件人、主题、正文、空附件列表、草稿版本和过期时间。服务计算规范化载荷哈希，批准必须来自用户并匹配当前草稿和待审快照。草稿修改会让旧提案失效；拒绝、过期、重复批准不得变成发送。J1 没有发送函数或 Gmail 连接器，批准只记录状态。未来接入发送时，必须在实际执行前再次验证账号权限、载荷哈希、有效期和幂等键。

审计仅记录事件类型、对象 ID 和时间，不写邮件正文或令牌。删除邮件、附件、真实同步、云模型、自动规则以及 API 入口均不在 J1 内。

## J2a：邮件转待办与来源追溯

用户确认后，Jarvis 可基于同一用户的合成邮件创建本地待办；创建和来源关联在同一数据库事务内完成。待办可查询原邮件的标题、发件人和分流状态；需要正文时再按权限读取邮件。来源不存在、属于其他用户或已缺失时不会暴露其他邮件，也不会留下半条待办。待办软删除后不可读取来源，恢复后可再次追溯。当前不接 Gmail 或真实数据，HTTP 接口也尚未添加。


## 审批快照保留（2026-11-06）

新发生的草稿编辑、重新准备审批、源邮件变化、拒绝和过期会清空当前行的审批载荷，同时保留状态、时间和摘要散列。读取或尝试批准已过期提案时才处理其过期状态，没有后台清理任务；此前已经关闭的旧记录不会自动回填清理。批准仍有效期间保留快照供核对；当前没有发送执行器。

这是当前数据库行的逻辑清理，不承诺删除 SQLite 旧页面、WAL、备份或系统副本；散列也可能泄露可猜测内容。真实资料仍不得进入当前数据库。验证：`backend/verification/verify_mail_snapshot_retention.py`。

## J29：本地虚构收件箱列表

新增按时间和 ID 倒序的有界分页；可筛选本地分流状态与优先级，也可查询主题/发件人。默认排除归档，列表不返回正文；owner 和 Jarvis 助手隔离。游标绑定筛选条件，不是加密的授权或跨页一致性快照，分页期间的修改可能造成结果移动。SQLite lower 不保证完整 Unicode 大小写匹配。没有连接真实 Gmail，亦未实现邮件发送。验证见 backend/verification/verify_mail_query.py 和 verify_http.py。

## J31：本地虚构草稿和审批列表

草稿按更新时间分页，待审批按到期时间分页；列表不返回正文、收件人和审批载荷，须打开详情后核对。已过期待审批项不显示，但列表读取不会主动修改其数据库状态或清空载荷，过期处理仍由详情访问触发。模拟审批不能发送邮件。验证见 backend/verification/verify_mail_queues.py 和 verify_http.py。
