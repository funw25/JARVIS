# Jarvis 新路线：进度基线与阶段计划

**状态：** 2026-11-14 更新。产品版本见 [产品基线](JARVIS_V2_PRODUCT.md)，技术目标见 [目标架构](JARVIS_V2_ARCHITECTURE.md)。本页是“现在在哪一步、下一步做什么”的入口；旧 `ROADMAP.md`、`CORE_IMPLEMENTATION_PLAN.md`、`STORAGE_SWITCH_PLAN.md` 保留为历史决策和实验记录，不作为新版阶段状态的唯一依据。

**总体判断：** **M1 虚构数据研究闭环已完成，M2 尚未启动**。纵向演示、同机离线环境、两次 v2 全量模型报告、20 条留出集及研究质量门禁均有证据，见 [M1 结果](M1_RESULTS.md)。v2 原集分类 81.1%、注入 8/8，留出集分类 85%、注入 4/4；两次全量关键决策 53/53 一致。噪声召回 0、优先级约 45–53%，模型不能接入真实资料或自动动作。M0 文档基线已形成。阶段不能按脚本数量计，M1 完成也不开放真实数据。

## 2. 阶段路线

| 阶段 | 核心交付 | 退出条件 | 依赖/风险 |
|---|---|---|---|
| **M0 重设基线（已形成）** | 产品版本、模块边界、统一数据模型、AI 评测协议、现状映射和明确下一阶段 | 三份文档互相一致；用户需求保留；旧方案作为历史材料可追溯 | 后续需求变化继续记入决策记录 |
| **M1 离线纵向闭环（研究范围已完成）** | 虚构资料从导入 → 队列 → 证据化建议 → 人工接受/修改 → 待办或草稿 → 审计；CLI 演示；固定集与留出集；模型对照 | 关键决策重复运行稳定；建议有原文证据；无外发；规则与模型质量/耗时报告；必跑检查零意外 SKIP | 两次 v2 全量、留出集、5 项离线检查与 `PASS_RESEARCH_ONLY`；噪声/优先级和真实资料质量转后续门槛 |
| **M2 可信本机底座** | 单一锁定运行环境、存储候选选择、可靠事务与作业、可信会话、独立备份/异机恢复、发布门禁 | G1 构建来源/许可、G2 独立评审、G3 恢复、G5 性能、G4 观察期均有证据；失败关闭；真实资料入口才允许评估 | 驱动可能需重建或替换；受限 DSH 故障可作为单独环境阻塞 |
| **M3 个人私测与 Gmail 只读** | 本地真实资料的主动导入和 Gmail 最小范围授权；可中断同步、来源覆盖、无正文出站默认 | 用户显式连接；撤权有效；同步游标与 404 回退；真实数据恢复演练；无外部写操作 | 受限 scope 验证/评估、用户同意、存储与密钥过门 |
| **M4 AI 与邮件受控动作** | 通过评测的摘要/待办/草稿；可逆整理规则；逐封批准发送；未知结果核对 | 质量指标达到事先确定阈值；审批快照失效、重试不重复外发；真实连接器权限审查通过 | 模型供应商、云处理与费用由用户具体选择 |
| **M5 产品界面与声音** | HUD 接用例 API、Windows 交付、按键语音、可访问性与性能基线 | 真实状态清晰、无假“已连接/已发送”；取消/失败/权限能被用户理解；无常驻监听 | UI 不得拥有执行器凭据；桌面封装方案按运行环境选择 |
| **M6 多设备与 X 轻量入口** | 设备注册/撤销、E2E 密文同步、网站登录、冲突恢复；X 书签/点赞有限导入 | 两设备离线/撤权/损坏/恢复对抗测试；Web 脚本信任评审；X 成本与授权范围可见 | 安全与平台成本都可能成为独立发布门槛 |
| **后续** | 微信内 Jarvis 会话/消息连接的官方可行性、更多来源、陪伴需求再梳理 | 分别立项和授权 | 不承诺个人消息“全部可查” |

M1 可以在 M2 的供应链工作开始前完成，因为它只用虚构资料；M3 必须等 M2 的真实数据门槛。M5 的视觉探索可并行，但接真实数据的界面验收仍依赖 M2–M4。M6 完成时才接近原需求中的“Windows + 网站 + 多设备 + X”的目标 V1。

## 3. 已完成阶段 M1：证据与遗留问题

1. **固定样本与契约。** 编写 40–60 条虚构邮件/帖子/笔记，覆盖真实产品会遇到的长线程、重复、时间、含糊承诺、噪声和提示注入；逐条标注应有的分类、待办与证据片段。数据必须标明虚构，不从用户账户抓取。
2. **画清一个纵向调用链。** 从现有 `synthetic_*` 服务抽取来源无关的 `Artifact`、`Suggestion`、`Todo`、`Draft`、`Approval` 合同；先适配现有表，不做全面重写。
3. **做可用演示。** CLI 或本机 API 能完整展示一条资料的导入、判断依据、用户修改、创建待办/草稿、审批状态与审计；无真实发送器。
4. **建立 AI 基线。** 先写规则基线，再用一个可替换模型实现离线对照；若需要云模型，先用虚构数据且逐次确认输入和预算。输出包含错误类型、来源支持率、耗时和费用，不用单个“总分”掩盖漏检。
5. **固定运行环境。** 选择一个 Python 版本，锁定依赖与哈希，提供无账户的重建/验证命令；把必跑测试与实验测试分开，必跑项出现 SKIP 即失败。M1 只需离线虚构链路的可重建环境；M2 还需另行解决加密驱动的供应链与正式运行环境。

**已完成：** 1–5 均有研究范围证据：规则/v1/v2 模型基线、20 条留出集、两次 v2 全量、Windows x64 同机干净目录重建；建议写入与动作生成前的证据/注入拦截已在虚构链路验证。一次无效 JSON 中断未计入完整报告，改为单条最多两次尝试且失败携带 ID；后续完整重复运行无重试。**下一步是 M2 可信本机底座，尚未启动**；先选存储驱动并关闭 G1 发布门禁漏洞，再做异机恢复和独立评审。噪声、优先级与第三方标注列入 M4 质量工作，不因 M1 研究门禁通过而放行真实邮件。

**M1 完成定义：** 非开发者能按说明运行一个虚构闭环；每个模型建议都有来源或明确“证据不足”；同一标注集可重复比较规则与模型；未经用户确认的外部动作数恒为零；演示、测试、结果和限制同日写入日志。未达到这些条件就留在 M1，不以“新增 N 个测试”推进阶段。

M1 不需要用户交出任何账户。若当时没有可用的真实模型，可先完成规则基线、标注集和评测框架；模型质量一栏保持“未验证”，`local_fake` 只能继续验证流程，不能替代模型基线或使 M1 提前通过。

## 4. 并行的 M2 研究包（不阻塞 M1）

- 对 APSW/SQLite3MC、SQLCipher 与其他可维护候选使用同一张选择表：源码到产物、许可证、Windows 构建、依赖维护、事务语义、密钥恢复、性能、迁移成本。**不预先选定现有驱动**。
- 修正 `G1_GATE=OPEN` 仍能以成功退出的发布门槛漏洞；合成回归 PASS 与安全放行结果分别报告。
- 备份检查模拟原设备及凭据管理器全部丢失，验证用户实际离线材料；修正 R2 35 天锁期与 4 周份数的策略冲突。
- 环境故障按 DSH 运行器/权限级别复现并反馈维护者，不能用完全权限结果冒充受限模式通过。

## 5. 项目记录与变更规则

每个阶段维护一条记录：**目标、日期、代码/文档链接、验证环境、PASS/FAIL/SKIP、未验证项、风险、下一步**。自动生成当前检查数量；旧结果保留日期，不覆盖历史。AI 质量报告与安全门槛报告分开。需求变更写入决策记录并说明对版本范围的影响。

2026-11-08 的 M0 重审只审视了本地仓库和官方平台接口文档；此后 M1 的虚构资料实现与回归结果见 [M1 结果](M1_RESULTS.md)。截至本页更新，未连接 Gmail、X、微信、小红书或模型账号，也未把实验加密候选批准为真实数据存储。旧文档中与此方案不同的结论仍作为历史记录，实施以本页及后续被确认的决策为准。
