# Jarvis 重设基线：产品定义与版本边界

**状态：** 独立重审后的建议方案（2026-11-08）。这份方案不以现有代码、既定驱动或旧里程碑为前提；用户已确认的需求仍作为约束。相关技术方案见 [目标架构](JARVIS_V2_ARCHITECTURE.md)，实施见 [交付计划](JARVIS_V2_EXECUTION.md)。

## 1. 产品定义

Jarvis 是**个人信息到行动的工作台**：把来源分散的内容安全地收进来，回答“什么值得看、为什么、下一步是什么”，让用户在同一处决定是否执行。它不是一个拥有邮箱和社交账号无限权限的自主代理。可信度来自可核对的原文、明确的数据边界、用户可改写的建议和可追踪的动作结果。

首个核心闭环是：**收集 → 识别待处理事项 → 给出依据和建议 → 用户确认或修改 → 形成待办/草稿/整理动作 → 查到结果和来源**。这个闭环要先在虚构资料上可用，再逐个接入真实来源。

## 2. 需求基线与建议调整

| 需求 | 来源状态 | 新版处理 |
|---|---|---|
| 邮件 triage、摘要、草稿、整理；待办完整主流程 | 用户明确提出 | 产品主线；邮件真实接入按只读、受控整理、逐封发送分阶段授权 |
| X 收藏/点赞、知识库、跨应用收集 | 用户明确提出 | 知识与手动收集先用；X 依 API 可用性、用量与成本单独放行 |
| Windows 桌面、网站登录、多设备、端到端加密同步 | 用户明确提出 | 保留为目标 V1 的能力；先做单设备私测，再做同步与 Web 安全验证；不可把“同步草案”称为已交付 |
| 电影感 HUD、按键语音 | 用户明确提出 | HUD 保留中央核心与环绕信息舱，但以任务可读性为先；语音只由用户按键启动。当前底层阶段不扩展界面 |
| 一个专用微信号与 Jarvis 聊、查微信/X 消息 | 用户曾提出；微信首版聊天对象限定 Jarvis | 独立的消息连接可行性项目。未证实可获准读取范围前，不承诺接管个人微信或“全部消息”；Jarvis 内聊天可先实现 |
| 陪伴助手与连续性记忆 | 用户要求暂缓 | 仅保留隔离通道和已有数据，需求重新梳理前不开发其人格、记忆或情绪功能 |
| 自动化权限 | 用户明确提出 | 本地低风险、可逆整理可按已启用规则执行；对外发送/发布及删除须逐项确认，模型本身没有执行凭据 |
| 隐私 | 用户明确提出 | 内容本地优先；云模型每次调用前显示接收方与必要片段；同步云端只存密文是目标，实施前须证明恢复和撤权 |

**建议调整的是交付顺序，不是删除长期目标。**旧计划同时铺开加密驱动、同步、HUD、社交账号与陪伴，使“功能原型通过”和“可处理真实资料”容易混淆。新版按可证明的用户闭环推进，每个真实来源单独过权限与恢复门槛。

## 3. 用户故事与验收

### 场景 A：每天的待处理队列

用户打开 Jarvis，看到“需要回复”“有明确承诺”“截止日期临近”和“待我确认”的分组。每个 AI 判断显示依据、来源时间与不确定性。用户可以修改分类，批量关闭误报；系统记录纠正以便评测，但不把个人内容自动用作训练数据。

### 场景 B：从资料到行动

用户保存一个链接、选中文本或文件。Jarvis 保留原文范围与来源，检索时先返回原文命中，再给摘要或待办建议。用户接受后，任务仍指向原资料；来源删除或更新时提示派生内容可能过期。

### 场景 C：邮件回复

Jarvis 提供回复草稿和支持该草稿的邮件片段。用户编辑后，审批页展示**账号、收件人、抄送、主题、完整正文、附件和最终版本**。批准只适用于这一版本；执行结果不明确时先向邮件服务核对，不盲目重发。

## 4. 版本定义

| 版本 | 用户能得到什么 | 明确不承诺 |
|---|---|---|
| **R0：可评估原型** | 虚构邮件/资料进入统一队列，待办和草稿建议有来源，审批及审计可演示；离线评测有基线 | 真实内容、真实模型质量、真实账号、可恢复的产品 |
| **R1：单设备私测** | 经过安全门槛后，Windows 本机保存用户主动导入的真实资料；本地待办、知识检索和恢复演练可用 | 多设备、自动外发、微信接管 |
| **R2：邮件主流程** | 用户显式连接 Gmail 后只读同步；再独立授权可逆整理和逐封发送；AI 摘要/草稿经模型质量与隐私测试 | 无审批发送、永久删除、全邮箱历史必然完整 |
| **目标 V1：多设备工作台** | Windows HUD、网站登录、端到端密文同步、按键语音、X 轻量入口、稳定备份恢复 | 个人微信全量历史、自动代聊、陪伴模式完整功能 |

R0/R1/R2 是**工程增量**，目标 V1 才是原需求的完整形态。若单人开发成本或平台权限导致目标 V1 的某项不能成立，须在发布前单独修订范围，不能静默省去。

## 5. 成功指标与失败条件

- **信息质量：** 用人工标注的离线样本衡量“重要邮件误报率”“明确待办漏检率”“摘要可由原文支持的比例”；上线阈值由样本基线和用户容忍度确定，不凭模型自报置信度。
- **行动可靠性：** 外发动作零未经批准；修改后的草稿旧批准全部失效；不确定执行结果有可见状态，不能把超时写成发送成功。
- **来源可追溯：** 每条建议可回到来源 ID、版本与证据片段；原文不可用时标明原因，不编造引用。
- **隐私与恢复：** 云模型输入与用户批准的预览一致；真实资料只进入已放行的存储；从独立备份和保存的恢复材料确实能恢复。
- **使用体验：** 本地队列与搜索有性能基线、键盘可操作，HUD 动效可关闭；这些指标须在目标规模数据上测，不以空库演示代替。

## 6. 仍需产品决策的事项

1. R1 的真实资料是否先限于用户主动导入，还是必须包含 Gmail；建议先主动导入，以验证存储和恢复。
2. 目标 V1 的网站端是否必须在桌面设备离线时独立解密与操作；这决定浏览器密钥和 OAuth 设计。
3. 云模型是否允许处理邮件正文、允许哪些提供方与预算；默认不发送，按具体请求确认。
4. X 账号接入的费用上限与历史范围；以连接时的开发者控制台和实际授权为准。
5. 微信内对话是长期必需能力还是可由 Jarvis 自有会话入口满足；平台允许的接口范围未证实时不写入首版验收。
