## 3. 纵向闭环

`python backend/usecases/m1_cli.py demo --id m1-005` 的实测路径：

```
artifact_imported  -> m1_artifact
suggestion_created -> m1_suggestion   (needs_reply / high / todo + draft / 证据逐字)
decision_recorded  -> m1_decision     (accept 或 modify + 用户改写)
todo_created       -> todo            (priority=high, status=open)
draft_created      -> m1_draft        (正文标"未发送"，无发送器)
```

已验证的分支（`verify_m1_pipeline.py`）：

| 场景 | 断言 |
|---|---|
| 正常接受 | 5 条审计事件齐全；todo 与 draft 同时生成 |
| 用户修改 | `{"todo": false, "title": ...}` → 不建 todo，只建 draft，标题用用户的 |
| 拒绝 | 不产生任何行，但写 `decision_recorded` |
| 重复文本 | 第二次导入写 `duplicate_of`，审计记录 `duplicate` 标记 |
| 注入（接受） | 分类 `injection`、优先级 high，且**不产生 todo/draft** |
| 发送能力 | 库内不存在任何"已发送"草稿；无发送器代码路径 |

### 2026-11-14 独立复现与稳定性

以下为 **v1 提示词的历史复现记录**；其当时的“是否关闭 M1”问题已由后续 v2 研究门禁结果更新，见本节末尾。

同一台机器、同一模型、同一 53 条样本，用项目内隔离目录启动 Ollama 后重跑两次。启动方式：把 Ollama **子进程**的 `USERPROFILE`/`HOMEDRIVE`/`HOMEPATH` 指向 `.jarvis-ollama\home`，并设置 `OLLAMA_MODELS=.jarvis-ollama\models`、`OLLAMA_NO_CLOUD=true`、`OLLAMA_HOST=127.0.0.1:11434`；服务日志明确打印 `Ollama cloud disabled: true`。GPU 发现失败（`llama-server --list-devices` 返回 `0xc0000005`），因此推理全部在 CPU，可用内存 7.1 GiB。模型摘要 `0edcdef3…`、大小 2,497,293,803 字节，与 `/api/tags` 一致；预热请求（要求输出 ready）6.8 秒返回。

| 指标 | 2026-11-09 基线 | 2026-11-14 第 1 次 | 2026-11-14 第 2 次 | 三次是否一致 |
|---|---:|---:|---:|---|
| 分类准确率 | 43.4% | 43.4% | 43.4% | ✅ |
| todo 准确率 | 83.0% | 83.0% | 83.0% | ✅ |
| draft 准确率 | 71.7% | 71.7% | 71.7% | ✅ |
| 提示注入召回 | 12.5%（1/8） | 12.5% | 12.5% | ✅ |
| 需回复召回 | 0/15 | 0/15 | 0/15 | ✅ |
| 优先级准确率 | 37.7% | **41.5%** | **39.6%** | ❌ 漂移 |
| 证据逐字率 | 98.1% | 98.1% | **100%** | ❌ 漂移 |
| 全量耗时 | 311.4 s | 342.0 s | 331.7 s | 约 ±10% |

结论：

- **可复现的部分**：分类、todo、draft、注入召回三次完全相同（43.4% / 83.0% / 71.7% / 12.5%），说明评测链路和模型摘要稳定。
- **不可复现的部分**：优先级 37.7 → 41.5 → 39.6（差 2 个项目）、证据逐字 98.1 → 98.1 → 100。即使设置了 `temperature=0`、`seed=42`，CPU 运行下的采样仍出现逐项差异；这是**模型侧非确定性**，不是评测脚本随机。
- 因此"同一标注集可重复比较"只在聚合指标层面成立；逐项对比需要每次保留 `details`（现已在报告中输出 id/gold/predicted/耗时/证据是否受支持），不能假设逐位一致。
- 证据文件只保留指标与哈希、不复制样本文本：[2026-11-09 基线](evidence/M1_OLLAMA_BASELINE_2026-11-09.json)、[2026-11-14 复现](evidence/M1_OLLAMA_REPLICATION_2026-11-14.json)。

**门槛判断：** 模型质量现在**已被测量**（不再是"未验证"），但结果是**失败基线**：需回复召回 0/15、注入召回 1/8、draft 71.7%，不能用于真实邮件或自动建草稿。M1 是否关闭取决于是否接受"已测量但质量不合格"的基线，这一点需要产品决定，不由脚本代替。

这只是固定 53 条虚构样本上的**失败基线**。模型漏检提示注入、漏判全部需回复项目，且有一处证据不受原文支持；不得用于真实邮件、自动待办或草稿，更不能参与外发。报告保留原始模型输出和错误项供下一轮提示词、规则前置检查与人工审核设计使用。离线脚本 `verify_m1.py` 不调用真实模型，因此它的 `M1_MODEL_QUALITY=NOT_CHECKED` 只描述该脚本，不覆盖这份独立评测。

`command` 提供方目前只支持“可执行文件从标准输入读提示、向标准输出写 JSON”的包装器，**不能直接把 GGUF 路径交给 `llama-cli`**；需另写包装器。OpenAI 兼容端点若非回环地址，CLI 要求显式 `--allow-remote`，并在运行前确认 53 条虚构输入和预算。[Ollama Windows](https://docs.ollama.com/windows)、[本机 API](https://docs.ollama.com/api/generate)。

- `local_fake` 只证明流程可跑，**不能**替代上述真实模型基线。
- `m1_eval.evaluate_model(rows, None)` 直接抛 `ModelUnavailable`，拒绝编造分数；`model_status()` 返回 `{"status": "未验证", "measured": false}`。
- 当前 `evaluate_model` 对非 `None` 参数只要求可调用，**尚未独立验证调用对象是哪个模型或是否真的调用了模型**。CLI 在成功运行后会记录提供方/模型名/端点与逐条结果，但这些是配置与接口响应证据，仍需核对本地模型摘要，不能把规则函数或 `local_fake` 传入后宣称真实模型测量完成。
- 验收标准保持：模型基线现已测量，但质量失败不能被测试数量或“评测已跑完”掩盖。
