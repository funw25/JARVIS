# M2：备份边界与发布预检（2026-11-14）

## 本轮结果

- 备份 CLI 之前在未设置模式时自动写入 `JARVIS_DATA_MODE=synthetic`，绕过了显式声明；现已移除。备份、恢复和备份任务先检查模式，未声明或声明个人数据时不解析备份、不创建目录、不读取或创建备份凭据。该声明不能识别被错误标为虚构的真实内容。
- 原备份任务测试删除了 Windows 凭据管理器中的默认备份口令和恢复码目标；现改为每次随机生成独立测试目标，清理仅限本次目标。**历史运行可能曾影响默认凭据，当前未检查这些凭据，也不能假设它们仍可用于恢复。** 今后必须用非敏感实验材料验证恢复；不要在未经核实的情况下依赖存储状态。
- 恢复原先只对 ZIP 条目名称做集合比较，重复名称会被掩盖；现要求正好三个不同的条目，上传检查也拒绝重复或缺失条目。恢复在解压前限制元数据 1 MiB、数据库 1 GiB，拒绝 ZIP 加密以及超过 m=262144 KiB、t=10、p=8 的 Argon2 参数，防止未认证输入造成无界资源消耗。低于原安全下限的参数仍被拒绝。这些限制可能拒绝更大的旧实验备份；正式容量和流式恢复仍需设计。
- 新增 `.github/workflows/release-preflight.yml`，手动触发、仅 `contents: read`，调用严格发布入口。它没有产物创建或发布步骤；本轮未触发 GitHub Actions，不能声称已在远端验证。没有正式发布流水线，也没有配置仓库侧权限或规则来阻止授权用户直接发布。将来创建正式打包发布流程时，必须把严格检查设为前置条件，并由仓库管理员配置权限保护。

## 验证

- 备份恢复专项通过：口令与恢复码同机恢复虚构数据，篡改、错误口令、重复条目、超大元数据、过高/过低 KDF 参数及未声明模式被拒绝，并发写入备份一致。
- DPAPI 虚构业务路径及 G1 虚构夹具验证通过；实际 `check_release.py` 返回 1，`G1_RELEASE_CHECK=BLOCKED`、`RELEASE_BLOCKED=G1`。
- 便携 CPython 3.14 全部 64 项本机合成回归：PASS=64、FAIL=0、SKIP=0。`driver_provenance` 的 PASS 是诊断执行成功，实际 G1 仍 OPEN，不能据此放行驱动或真实数据。3.13 对照未重跑。
- 本机普通沙箱读取现有依赖目录遭拒，相关验证在获准的提权环境执行。没有访问真实账户、远程备份或真实资料；没有验证异机恢复、独立审计或远端工作流。

## 尚未完成与下一阶段

当前处于 M2 可信本机底座，真实资料和正式发布仍关闭。下一步依次建立可复核驱动构建及完整许可证/SBOM，获取独立评审，完成异机恢复与性能、观察期验证；随后设计并验证真正的发布流水线与仓库权限，以及真实资料启用路径。上述独立评审、第二设备与时间观察不能用本机自测替代。

备份计划任务不会自动继承交互 PowerShell 的变量：旧任务如果没有明确的 synthetic 模式会失败关闭。不要为绕过限制把真实内容标为虚构；重新启用计划任务前，须确认任务进程模式并使用虚构数据演练。
