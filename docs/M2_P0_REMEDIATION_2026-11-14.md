## 1. 证据与旧报告

`m1_rules.evidence_supported` 要求所有证据为非空、非纯空白且逐字出现在原文中；模型解析器与建议入口执行相同边界，评测不再把空片段计入非空或逐字率。`export_m1_evidence.py` 用原始报告和固定虚构样本重新核验，并保存字符位置而不复制样本文本。`check_m1_quality_gate.py` 校验这些位置，缺少位置或位置无效的精简报告不能通过；历史三份 v2 原始报告哈希未变，按新规则重新导出后研究门禁仍通过。

这些位置和摘要是可复核的记录，不是防止有仓库写权限的人伪造报告的签名，也不代表模型的推断在语义上成立。

## 2. 重复执行及旧数据

迁移 `0019_m1_materializations.sql` 给每个决定建立唯一的执行结果记录。生成待办、草稿、审计事件和结果映射在同一事务的保存点内；异常回滚后可重试。历史数据库没有决定到生成结果的关联，迁移会把已有决定标为 `legacy_unknown` 并拒绝重放，后续需人工核对，不能自动猜测它是否已执行。

已验证同连接重试、两个线程、实验加密库上的两个进程，以及写入待办后注入异常的回滚。没有证明长期高并发、断电或全部异常条件。

## 3. 实验加密存储

`JARVIS_STORAGE_ADAPTER=dpapi-vault` 只能在 `JARVIS_DATA_MODE=synthetic` 且 `JARVIS_VAULT_DIR` 指向已初始化实验 vault 时使用。应用通过 DPAPI 包装的密钥打开现有加密库，不接受 `JARVIS_APSWMC_KEY`；未知适配器、明文适配器搭配 vault、冲突路径和错误密钥均拒绝，不回退到明文。`open_vault` 也修复为调用方发生异常时回滚，而非误提交。

验证包括应用迁移、虚构业务、数据库与当次存在的 WAL/SHM 文件中不出现测试标记、普通 SQLite 无法打开、双进程幂等与错误密钥拒绝。这些检查不能证明文件系统其他副本、系统页面文件或 Python 内存中的密钥已被保护。模式声明无法识别真实内容，不能把私人资料输入合成模式。

DPAPI 常规用户范围通常受用户与机器约束；单靠 DPAPI 不构成异机恢复。SQLite3MC 文档描述数据库和日志加密，但实际项目 wheel 的源码到二进制关系仍未证实。参考 [Microsoft DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)、[SQLite3MC 文档](https://utelle.github.io/SQLite3MultipleCiphers/)。

## 4. G1 与发布入口

`verify_driver_provenance.py` 默认是合成实验的诊断，使用 `--release` 时检查完整 G1 证据，缺失即非零退出。`tools/release/check_release.py` 先运行严格 G1；即使 G1 将来通过，在其他真实资料门槛尚无实现之前仍返回阻止。检查要求驱动目录内每个文件都被清单锁定、随包许可文本、源码锁定、构建脚本、两次构建日志及相同产物摘要、SBOM、依赖审查和独立评审记录；证据文件路径与哈希均核对。本轮观察到当前清单只锁定 3 个文件，驱动目录另有 91 个未锁定文件，数量可能随缓存变化。测试中的“批准”材料是临时虚构夹具，不是对当前驱动的批准。

未来的 `docs/driver-manifest.json` 须包含 `release_g1`：`state`、两位不同构建者 `builder`/`second_builder`、独立 `reviewer`、带时区的 `reviewed_at`，两次构建出的驱动哈希，以及按名称提供路径和 SHA-256 的证据映射。当前门禁要求两个构建产物与已安装驱动逐字节一致；若未来需要认可可解释的非确定性差异，须先独立审查并修改门禁，不允许以缺失证据放行。记录中的姓名本身不能在技术上证明真实身份。

当前实测输出为 `G1_GATE=OPEN`、`G1_RELEASE_CHECK=BLOCKED`、`RELEASE_BLOCKED=G1`，退出码 1。检查是防止误操作的工程控制；仓库内自述不能证明评审者身份，且没有仓库配置能够阻止有外部发布权限的人绕过脚本直接发布。未来建立正式打包/发布流水线时，必须强制调用此入口并设置对应仓库权限，不能以诊断结果代替放行。

### 已补充的候选来源证据

- 根据 [PyPI 3.54.0.0 元数据](https://pypi.org/pypi/apsw-sqlite3mc/3.54.0.0/json)，下载并核对了源码包 SHA-256 `60a021cd9f6c8f3e2aa6cb54e197cb344379d5eb9a688b7647a136fc24956db4`，以及 Windows CPython 3.14 wheel SHA-256 `ce02879c647746af870ee6081fa1b1882b1bd6b9ab559a31008cb887a7726815`。文件位于 Git 忽略目录；[来源锁](../tools/driver/candidate-inputs.json)记录 URL、大小和哈希。
- wheel 的 90 个非 `RECORD` 文件与当前安装逐字节一致；安装后的 `RECORD` 保留 wheel 的 91 条原记录，额外包含 26 条安装生成项。它支持“安装文件与该公开 wheel 一致”，不证明 wheel 从同版源码构建。
- 源码包包含合并的 `sqlite3.c`，其哈希 `3153b2f567aceacd1f80a845e77f7b3c632e9af130af07343ee4bbcdcff31c60`，版本宏标示 SQLite 3.54.0、SQLite3MC 2.6.1；尚未证明其与 wheel 的构建关系。公开上游 `v2.6.1` 标签解析到提交 `45d4ed3487bc02cb08ac73afff47c031c3f88ee0`，该提交的 [SQLite3MC MIT 许可证](https://github.com/utelle/SQLite3MultipleCiphers/blob/45d4ed3487bc02cb08ac73afff47c031c3f88ee0/LICENSE)已按来源锁下载、核对哈希；它**仍未随当前 wheel 安装**。
- 合并源码中两处 OpenSSL 字样出现在兼容性注释，不能据此断定实际链接了 OpenSSL，也不能单靠字符串搜索排除依赖。尚缺源码与产物的构建映射、完整实际依赖清单和独立构建。
- 复核命令：`tools/driver/fetch_candidate.ps1 -VerifyOnly` 核对已下载材料；`python tools/driver/verify_candidate_inputs.py` 核对压缩包、合并源码、wheel 与安装文件，不提取或执行下载源码。若需重新下载，脚本可选 `-Proxy`，按锁定哈希检查后才保存。PyPI 元数据与文件哈希来自同一发布渠道，尚不是独立签名或第三方构建证明。

合并源码提示某些 SQLite 临时文件不加密；当前实验适配器设置内存临时存储，这不等于所有系统副本、页面文件或临时文件均已验证安全。正式版本必须限制可执行 SQL 并单独验证泄露面。
