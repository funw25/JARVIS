# Jarvis 底层风险整改方案

**日期：** 2026-11-08；事实复核：2026-11-09
**状态：** 方案分析；未放行真实数据，也未代替 G2 独立评审。
**输入：** 用户列出的 39 项运行环境、供应链、正确性、备份、门禁和流程问题。编号沿用该列表。
**当前边界：** 最近记录的 `verify_all.py` 是 **57 个脚本项 PASS / 0 FAIL / 0 SKIP**；其中一项 `driver_provenance` 只核对现有清单/哈希等诊断，打印 `G1_GATE=OPEN` 却仍以 0 退出。因此“57 PASS”混合了合成功能检查与未闭合的供应链诊断，不能证明驱动可承载真实数据、长期运行或异机恢复。功能回归计数和 G1 发布门槛必须分别报告。

**环境观察（两个 runner/会话，不合并）：** 先前 Codex 工具会话的默认权限曾执行只读命令与文档检查；用户报告当前 DSH 会话在 `workspace-write`/`read-only` 下连 `Get-ChildItem` 都以 `3221225794`（`0xC0000142`）退出，仅 `danger-full-access` 可用且审批提示被禁用。前者不能证明后者已修复，也不能由后者否定前者。后续复测须记录 runner、会话令牌、沙箱模式、命令与退出码。

## 1. 四条实施路线

| 路线 | 做法 | 能解决 | 代价和适用结论 |
|---|---|---|---|
| A：维持实验状态 | 继续只用合成数据，修文档、验证链与备份演练，不切换真实数据 | 可及时发现设计与测试问题；保留现有研究成果 | 成本最低；**不能**当作真实数据放行方案 |
| B：可追溯地构建现有 SQLite3MC + APSW（建议主线） | 固定源码提交、算法和编译参数，生成完整许可证、SBOM、构建日志和产物哈希；两次独立构建；再加强存储适配合同 | 主要针对 7–12、14–19、28–29、37–38 | 保留现有业务接口，但维护自建 wheel 和手写适配器；必须经独立评审 |
| C：替换加密驱动 | 先选择有可维护 Windows/Python 发行链的候选，再做数据格式、适配器和恢复格式迁移 | 若 B 的来源/维护或适配器语义无法收敛，可减少对现有驱动的依赖 | 重做和双格式兼容成本高；不能仅凭“SQLCipher 更成熟”选用当前已知不合格 wheel |
| D：降低首发范围 | 将首发限定为本机单设备、手动导入且明确的本地备份；外部账户和多设备以后开放 | 减少 21–27、30、37–39 的同时暴露面 | 不能省略密钥恢复、真实数据门禁、G1/G2/G5；需用户重新确认产品范围 |

**推荐组合：** A 作为当前安全边界，B 作为技术主线；C 仅在 B 无法通过来源、性能或正确性验收时启动。D 是产品范围决策，不应被用来绕过存储安全门槛。

## 2. 按问题组整改

| 编号 | 优先级 | 具体方案与通过条件 |
|---|---|---|
| 1–6 运行环境 | P1 | 对 DSH 受限令牌故障保留最小复现并反馈运行时维护方；本机使用绝对路径和单一项目 Python 启动脚本。固定 CPython、依赖版本/哈希及离线安装说明，统一到一个依赖目录；在干净环境重装并运行关键检查。受限模式恢复须由独立 `cmd` 和 Python 启动测试证明；`danger-full-access` 不是修复。临时目录清理采用显式关闭句柄、延迟重试、残留计数；不把 `ignore_cleanup_errors` 当作清理成功。 |
| 7–13 供应链 | P0 | 先修正 D6：当前 APSW/SQLite3MC 的 OpenSSL 依赖**未证实**，SQLCipher 候选的已知结论不可外推。固定源码与构建脚本；核对 wheel 动态依赖和构建记录，列出实际算法实现、源码 commit、组件版本、许可证、SBOM、二进制哈希；做第二次独立构建和差异解释。G1 未通过前只用合成数据。 |
| 14–19 正确性 | P0 | 把 APSW 兼容层限制在最小、明确的 sqlite3 合同；所有游标/事务显式关闭，用故障注入覆盖提交、回滚、异常映射和陈旧快照。增加多进程、长读事务、写锁超时、进程被杀、迁移中断测试。连接配置由不可变对象在启动时一次传入，拒绝相互冲突的数据库路径/适配器/数据模式；避免测试进程共享可变环境。`integrity_check` 的完整扫描移至备份/维护时或定期任务；启动时保留必要的密钥、schema 和快速一致性检查，并测大库成本。此改动须由独立评审确认。 |
| 20–27 密钥和备份 | P0/P1 | 明确 Python `bytes` 不能保证擦除，威胁模型如实写明；需要更强保证再考虑原生密钥边界。每份最新本地及远端归档须定期在**空目录**仅用用户实际保存的恢复材料演练；演练不得从原 vault/凭据管理器偷取密钥。恢复码显示、用户离线保存、二次确认与“材料丢失即无法恢复”提示并行；无法技术性证明纸质抄写。审计元数据最小化并做完整性/轮转设计。桶锁 35 天与每周 4 份冲突：至少保留能覆盖锁期的份数，或缩短锁期；报告期望 N、实际 M、锁定待删 K，锁期后再清理测试残留。归档名改随机不透明标识，精确时间与 key_id 放在本地受控清单。 |
| 28–30 真实数据门禁 | P0 | 不把 `JARVIS_DATA_MODE=synthetic` 当作内容识别。真实数据接入入口在编译/配置上默认不存在，所有联网连接器和导入器要求单独开启；生产启动要求签名/哈希匹配的驱动清单及 G1/G2/G3/G5 放行标记，缺失时拒绝，不允许自动降级明文。对“换机恢复”采用独立 Windows 用户/另一台机器或一次性隔离环境验证；同机演练只标记为同机。 |
| 31–36 流程 | P1 | 建立本机离线 CI 等价脚本与可用时的 CI：关键检查零 SKIP；实验项可单列但不得计入发布门槛。为每项记录耗时、环境指纹与运行日期，给整套/单项设预算并定位慢项；并行只用于隔离目录和无共享凭据的检查。测试 OS 凭据使用唯一目标名与 `finally` 清理，保留可运行的残留盘点。README/状态页引用同一个生成的机器结果，历史数字仅保留在日志。已经推送的截图不能靠删除工作区撤回；单独做内容复核与必要的外部处置决定。 |
| 37–39 验收 | P0 | G1 需要源码→构建→产物证据，不是仅有检测脚本；G2 须由未参与实现者复核并逐条回答评审包问题；G4 连续 14 天有运行与失败记录；G5 测真实目标规模的启动、读写、备份与恢复。轮换提醒接入可见通知和事件触发，但轮换仍由用户确认；先保证泄露疑虑时能立即轮换并验证旧钥失效。 |

## 3. 执行顺序与停止条件

1. **立即整理事实（P0）：** 纠正 D6、评审包和状态页的错误归因；标记旧数字为历史值。把 G1 检查结果与完整回归结果分开显示。停止条件：所有面向评审的当前描述一致，不再把 SQLite3MC 说成已证实使用 OpenSSL 3.6。
2. **固定可复现环境：** 单一解释器和哈希锁、干净安装、受限沙箱故障最小复现。停止条件：同一命令在新环境中重复得到相同关键检查结果；受限模式仍坏则明确登记为外部阻塞，不用全权限运行结果冒充沙箱验证。
3. **证明候选驱动和适配器：** 完成 B 的构建证据、事务合同、多进程压力和大库基线。任何来源不明、许可证缺口、错误密钥误开、丢更新或静默明文回退都阻断真实数据。
4. **证明备份可恢复：** 以模拟原机器完全丢失的环境，从最新远端归档和离线材料恢复；对账保留数量，检查审计和测试残留。失败即停止真实数据计划。
5. **独立评审与观察期：** 回答评审包全部问题，跑 G4/G5 并记录趋势；只有门槛全部有证据才讨论首次真实数据导入。用户仍需明确连接服务和授权外部操作。

## 4. 需要明确的设计决策

- **首发是否允许多设备和真实账户？** 建议先不开放，直到上述门槛完成；这不改变长期产品目标。
- **当前 APSW 路线能否完成可维护的 Windows 构建？** 若 G1 或适配器语义无法收敛，启动 C 的替换评估，而不是继续增加补丁。
- **备份锁期与保留份数如何配套？** 先按时间窗口算保留份数，再实现对账；“保留 4 份”不能与 35 天锁定同时视为硬保证。
